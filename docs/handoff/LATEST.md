Full design is in `docs/coveo-source-spec.md`'s new `pokemonoverview` section, with a numbered console-steps list for whoever picks this up next — **do not treat it as done.**

Docs read (per CLAUDE.md's process rule):
- `docs.coveo.com/en/mahe0350/` (Web scraping configuration) — read for the metadata-extraction rule syntax. **Confirmed and load-bearing**: a selector matching multiple nodes always returns a multi-value array (no join operator in the syntax), and CSS's `::text` suffix returns each matched element's *full* inner text as one array entry — unlike XPath's `text()`, which only returns direct child text nodes and fragments on nested inline tags. This second point isn't previously documented in this repo and directly explains a real bug found this session (below).
- `docs.coveo.com/en/o3ca0547/` (Index metadata) — read to double-check the multi-value-by-default claim from a second angle; corroborated it, added nothing new.
- `docs.coveo.com/en/1833/index-content/manage-fields` (Manage fields) and a targeted search — read to confirm "Multi-value facet" is the only mechanism this console's String field type offers for storing more than one value (no independent "multi-value, not a facet" option). Matches this project's own established pattern (every other multi-value field in `docs/coveo-source-spec.md` is typed Multi-value facet), so treated as confirmed rather than divergent.

Real bug found and designed around, not just theoretical: the originally-planned selector (XPath `text()` on the four intro `<p>` elements, matching this file's usual convention) was tested against real fetched Charizard HTML with `lxml` and returned **15** fragments for 4 paragraphs — XPath `text()` split on every nested `<a>` link (Charizard/Fire/Flying/Generation-1 are all links inside the prose). Switched to CSS `ul.list-nav.panel.panel-nav ~ p::text`, verified against Pikachu (2 paragraphs)/Sprigatito (3)/Garchomp (4)/Charizard (4) — real paragraph counts vary, always exactly the paragraphs between the entity-nav `<ul>` and `#dex-basics`, confirmed safe unscoped since the other 2 occurrences of that `<ul>` class (Moves/Sprites tab navs) have no `<p>` siblings on any sample page.

Second real mismatch found: extraction is inherently multi-value (per the docs above), but `mapPokemonResult.ts` already reads this field with `asString()`, which returns `undefined` for anything that isn't a plain string — so a naively-configured multi-value `pokemonoverview` would silently blank the PDP, not error. Resolved by following this file's own existing `pokemonweaknessesraw`/`resistancesraw` → postConversion IPE → clean-field pattern: extraction lands in `pokemonoverviewraw` (multi-value), a new IPE joins with `"\n\n"` into single-value `pokemonoverview`, matching the frontend's existing contract exactly. IPE code, field types, and the full numbered console-application sequence are in `docs/coveo-source-spec.md`.

**Status: Test not verified (nothing applied to the console), Full not touched, no rebuild triggered.** Everything above is design + real-HTML content verification only. `docs/coveo-source-spec.md` is up to date with the full spec and is marked "not yet applied" throughout — read it before doing the actual console work next session.

## Fortieth session — LCP fix: `priority` on the three above-the-fold sprite/art images

Lighthouse flagged three LCP checks (missing `fetchpriority="high"`, lazy-loading, not discoverable in the initial document) against `PokemonImage.tsx` and `ImageSlot.tsx`, neither of which forwarded a `priority` prop to `next/image`. Added an optional `priority` prop to both and wired it to `true` at three call sites: the PDP hero (`PokemonHero.tsx`), the first tile only of the search results grid (`ResultList.tsx`, `index === 0`), and the homepage banner (`page.tsx`'s `ImageSlot name="homeBanner"`).

The homepage banner fix is complete — `CONTENT.art.homeBanner` is a static import, so it's already in the server-rendered HTML and `priority` alone should satisfy all three checks. The PDP and search-grid fixes are partial: both `PokemonDetailPageClient.tsx` and `ResultList.tsx` fetch their Pokemon data client-side in a `useEffect` after mount, so the `<img>` tag itself doesn't exist in the initial server HTML regardless of the `priority` prop — the "discoverable in initial document" check will keep failing there until Coveo-fetched data is available at SSR time. `generateMetadata` in `pokemon/[name]/page.tsx` already does a server-side lookup (`fetchPokemonMetadata`) that includes `imageUrl` for OG tags but discards it rather than passing it down; closing the PDP gap would mean threading that server-fetched data into the client component as initial state — a real change to the client-only data-fetching pattern, not just an image attribute, and one that touches the "no server layer" posture in `docs/adr/0004`.
