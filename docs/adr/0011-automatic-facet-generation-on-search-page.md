# 0011: Automatic Facet Generation on /search, static pills on the home page

Status: Accepted

## Context

The tenth session fixed a real bug: `Facet`/`FacetSpeed` components built their Headless controllers with no explicit `facetId`, and the app's `engine` is a persistent singleton across the whole SPA session. Navigating away from `/search` and back never deregistered the old facet (Headless has no deregister API — only `disable()`, which doesn't remove the registration), so each remount minted a new auto-suffixed facetId (`pokemontype_2`, `_3`, ...) and warned `"A facet with field ... already exists"`. `SearchSummaryBar.tsx`'s breadcrumb `<span key>` was built from `breadcrumb.field` (not unique across differently-`facetId`'d duplicates), producing React's "two children with the same key" error live. Fixed at the source by pinning `facetId: field` on every manual facet — `registerFacet`'s reducer is a no-op when the id already exists, so a remount now silently reuses the existing registration.

That fix prompted a broader question: does Coveo's real **Automatic Facet Generation** feature remove the need for hand-built facet components (and their bug surface) entirely? Investigated by reading the installed `@coveo/headless` source directly, not just docs — `controllers/facets/automatic-facet-generator/`, `controllers/facets/automatic-facet/`, `features/search-parameters/search-parameter-serializer.js`, `controllers/breadcrumb-manager/headless-breadcrumb-manager.js`.

## Findings

- `buildAutomaticFacetGenerator`'s `state.automaticFacets` is derived fresh from `engine.state.search.response.generateAutomaticFacets` on every read — there is no persistent per-mount registration at all. Automatic facets **structurally cannot** hit the duplicate-registration bug class above, unlike manual `Facet`.
- **Automatic facets do restore from a URL** — `search-parameter-serializer.js`'s `SearchParameters` interface has a dedicated `af?: Record<string, string[]>` key (`facetSearchParamRegex`'s `af-` prefix), serialized/deserialized the same way as manual facets' `f-`. Confirmed live: selecting an automatic facet value produces `?af-pokemontype=Bug` in the address bar, and reloading that URL restores the selection correctly, in both dev and a production build. (An earlier pass at this ADR incorrectly concluded `af` didn't exist, based on misreading `isValidBasicKey`'s list rather than the full `SearchParameters` interface — corrected here.)
- **STRING fields only** — confirmed both in Coveo's docs and by the generator only ever reading `generateAutomaticFacets.facets`, which the index only populates for eligible Facet/Multi-value-facet STRING fields. `pokemonspeed` (Integer, `buildNumericFacet`) cannot move over.
- `AutomaticFacet`'s interface (`toggleSelect`, `deselectAll`, `state: {field, label, values}`) has **no facet-search method** — unlike `Facet.tsx`'s `searchable` variant used by `FacetAbilities`. Abilities has a few hundred distinct values; a plain top-N list with no search box would be a real usability regression for finding one specific ability.

## Decision

**On `/search`**: replace `FacetType`, `FacetGeneration`, `FacetEggGroups`, `FacetWeaknesses`, `FacetResistances` (5 components) with one `AutomaticFacets.tsx` built on `buildAutomaticFacetGenerator`. Enable the **Facet Generator** field option (admin console, Fields page) on exactly those 5 fields — all already Facet/Multi-value facet-enabled, so no other config change needed. `AutomaticFacets.tsx` preserves the curated Chip rendering for `pokemontype`/`pokemonweaknesses`/`pokemonresistances` (color-coded, matching what the removed components did) via a small field-based switch, rather than losing that visual treatment. **Kept manual**: `FacetSpeed` (numeric, ineligible for Facet Generator) and `FacetAbilities` (needs facet-search, which automatic facets don't support). `SearchSummaryBar.tsx` gained a third breadcrumb block for `automaticFacetBreadcrumbs`.

**On the home page**: replace `BrowseByType.tsx`'s live `buildFacet`-backed grid with a static list of the 18 real Pokemon types (`POKEMON_TYPES` in `src/coveo/typeColors.ts`), linking into `/search` pre-filtered by type. No live query on the home page at all, and no per-type counts (an accepted tradeoff — `/search` itself still shows live counts once landed). Hardcoding the type labels doesn't violate the no-fabricated-data principle (`CLAUDE.md`/`PRODUCT.md`): Pokemon types are a fixed, closed, real taxonomy, not Pokemon-specific data being invented.

**Two real bugs discovered mid-implementation and fixed as part of this same change, not shipped broken:**

1. `buildTypeSearchHref` previously generated `/search?f-pokemontype=<value>`, which only pre-filters results if a *manual* facet is registered under `facetId: "pokemontype"` on `/search`. Once `FacetType` was removed in favor of `AutomaticFacets`, nothing on `/search` claims that facetId anymore, so that link would have silently stopped filtering anything (an automatic facet's own URL key is `af-pokemontype`, not `f-pokemontype` — the two are not interchangeable). Fixed by switching `buildTypeSearchHref` to an `aq` (advanced query) expression — `@pokemontype=="<value>"` — the same exact-match pattern already used by the Pokemon detail and compare pages. This also sidesteps any dependency on which facet mechanism happens to own the field on `/search`.
2. That fix then exposed a second, unrelated pre-existing bug: `/search` never registered the `advancedSearchQueries` Headless reducer (only the detail/compare pages did, via `loadAdvancedSearchQueryActions`, before their own `updateAdvancedSearchQueries` dispatch). `search-parameter-manager.js`'s `getAq()` returns `{}` whenever `state.advancedSearchQueries === undefined` — so an `?aq=...` URL param on `/search` silently round-tripped back to a bare `/search` with nothing filtered, confirmed live via a captured request showing no `aq` in the actual Search API body at all. Fixed by calling `loadAdvancedSearchQueryActions(engine)` in `SearchUrlSync.tsx` before `buildUrlManager` constructs (which is what synchronously dispatches `restoreSearchParameters` from the URL). This bug predates this session entirely — `aq` was simply never exercised via a `/search` URL before the Browse-by-type pills needed it.

## Consequences

- Net code reduction: 5 facet components + `BrowseByType`'s controller logic deleted, 1 new component added.
- Automatic facet selections restore from a URL exactly like manual ones (`af-<field>=<value>` vs `f-<facetId>=<value>`) — no shareable/bookmarkable-URL regression from this migration.
- `/search`'s `aq` param (used by the Browse-by-type pills) now actually works, having silently done nothing before this session — a genuine capability gain, not just neutral.
- The exact facetId-collision bug class this session opened with cannot recur for any of the 5 migrated fields, by construction (no persistent registration to collide).
- If `pokemonabilities` or `pokemongrowthrate` (or any other STRING facet-eligible field) is ever considered for Automatic Facet Generation, re-check the facet-search constraint above before assuming it's a drop-in move (URL restoration is no longer a concern, now confirmed to work).
