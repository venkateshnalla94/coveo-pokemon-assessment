# 0010: Shared `useControllerState` hook for Headless controller subscriptions

Status: Accepted

## Context

The eighth session found a real crash in `SearchBox.tsx`: "Cannot update a component (`SearchBox`) while rendering a different component (`SearchUrlSync`)". Root cause was `SearchBox`'s original `.subscribe()` + `useEffect`-driven `setState` pattern — a Headless controller can notify its subscribers synchronously from another component's render (here, `SearchUrlSync`'s `buildUrlManager` constructor dispatching `restoreSearchParameters` mid-render), and React doesn't allow a `setState` call during another component's render. That session fixed `SearchBox.tsx` specifically, via `useSyncExternalStore` with a cached-snapshot ref and a stable `subscribe` callback, and flagged — but didn't fix — ~11 other components using the same vulnerable pattern: `Facet.tsx`, `Pager.tsx`, `FacetSpeed.tsx`, `DidYouMean.tsx`, `GeneratedAnswer.tsx`, `ResultList.tsx`, `BrowseByType.tsx`, `SearchSummaryBar.tsx` (3 controllers), plus the home, detail, and compare pages. They were confirmed inert at the time only because `SearchBox` was the sole controller duplicated into a persistent layout — not a guarantee that stays true as the app grows.

Separately, a sibling take-home project (`/Users/venalla/coveo-assesment`) uses a different shape entirely: one custom hook (`useHeadlessCommerce`) owns engine/controller construction, subscription, and produces a single flattened snapshot; components never touch a controller directly. This was raised as a candidate pattern to adopt here wholesale.

## Decision

Adopt the "component → hook → engine" principle, but not the sibling's exact shape. That sibling hook works because it owns one cohesive commerce feature end to end. This app's `/search` page instead composes ~10 independent, loosely-coupled Headless controllers built directly against one already-existing shared engine (facets, pager, sort, RGA, summary, URL sync) — collapsing them into one mega-hook would produce one hook with a large flattened prop surface and make controller composition (e.g. `SearchUrlSync` needing to run its dispatch before `SearchBox` reads engine state — see `SearchUrlSync.tsx`'s doc comment) harder to reason about, for no real benefit.

Instead, extract only the subscription mechanics — not the whole controller — into one small reusable hook: `src/coveo/useControllerState.ts`. It's the exact recipe `SearchBox.tsx` already proved correct (`useSyncExternalStore` + a snapshot cached in a `useRef`, refreshed only inside the subscribe callback + a `useCallback`-stabilized `subscribe` function), generalized to any object shaped `{ state: TState; subscribe(listener): () => void }` — which is every Headless controller. Every component/page that feeds a controller's `.state` into React render state now calls this hook instead of hand-rolling (or, until now, not noticing it needed) the same fix. `SearchBox.tsx` itself was switched over to call the extracted hook rather than keep its own inlined copy.

`SearchUrlSync.tsx`'s own `urlManager.subscribe()` was deliberately left untouched — it drives `router.replace()`, not React state, so it was never in the vulnerable class to begin with.

## Consequences

- This closes the eighth session's audit item for real: every controller subscription that feeds a React render goes through the same hardened mechanism, so this exact crash class can't recur if a controller is ever duplicated into a persistent layout again — the fix no longer depends on remembering to re-derive it at each new call site.
- Callers whose controller is always defined use the pattern `useControllerState(controller) ?? controller.state` to keep their state's type non-optional (the hook's return type is `TState | undefined` since some callers, e.g. `SearchBox`/`GeneratedAnswer`, have a genuinely optional controller when Coveo isn't configured or the org lacks a capability).
- The sibling project's one-mega-hook-per-feature shape was considered and explicitly rejected for this app's `/search` page composition — this is a deliberate divergence from that pattern, not an oversight, should it come up again.

## Related: the `executeSearch/rejected` console error

While investigating this, a separate reported console error — `Action dispatch error search/executeSearch/rejected` — was root-caused. Several pages (`src/app/page.tsx`, `SearchUrlSync.tsx`, the detail page) each dispatch their own `executeSearch` on mount against the same module-level engine singleton (`src/coveo/engine.ts`). Navigating between them (or, per a live repro, even a cold single-page load under real network timing) can race two `executeSearch` dispatches; Headless correctly cancels the stale one, but its logger middleware (`app/logger-middlewares.js`) reports every cancelled/rejected action via `logger.error` unless `payload.ignored` is set — and the installed `executeSearch` thunk processor never sets that flag. Confirmed via a live repro (cold-load, cross-page navigation, browser back/forward, in both dev and a production build) that results and facets are correct every time this fires — it's cosmetic, not a real failure.

Headless's public `configuration.loggerOptions` only exposes `level` (global) and `logFormatter` (reshapes the log object, can't drop it) — no way to suppress just this one message through the public API. Since the requirement was that this line must never appear during a live exec demo or on the hosted (Vercel) app, and raising the log level globally would also hide other, potentially real, Headless warnings, `src/coveo/engine.ts` filters `console.error` narrowly: it drops only calls whose args include this exact message text, and forwards everything else unchanged. This doesn't change what happens (the stale request is still correctly cancelled) — it only hides a known-benign, third-party log line. If a future `@coveo/headless` version changes this message text, the filter simply stops matching and the line reappears (fails open).
